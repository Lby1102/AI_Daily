# AI 资讯清洗、生成与 HTML 输出模块设计文档

## 1. 文档目的

本文档定义项目中模块 2～4 的职责、处理流程、输入输出、模型调用方式、人工反馈机制和首阶段验收标准，用于指导近期开发与模块间联调。

当前目标是先跑通最小闭环：从模块 1 提供的原始 TXT 中筛选 AI 资讯，生成包含 2 条资讯的文章，并输出一个 HTML 文件；宣传部审核不通过时，可以通过 TXT 反馈文件要求系统重新生成。

## 2. 项目范围

### 2.1 本模块负责

1. 读取模块 1 生成的原始资讯 TXT。
2. 从原始内容中识别、清洗和筛选 AI 相关资讯。
3. 综合相关性、时效性、可信度和热度选出候选内容。
4. 在评分时适当提高纯 AI 软件类资讯的优先级。
5. 调用 DeepSeek V4 分别深度凝练两篇入选文章并生成完整公众号长文。
6. 将文章排版并输出为 HTML 文件。
7. 接收宣传部提供的 TXT 反馈，并据此重新筛选或改写。

### 2.2 本模块暂不负责

- 原始数据爬取。
- 前端页面或人工审核界面。
- 图片生成与图片插入。
- 微信公众号草稿箱推送。
- 微信公众号 HTML 兼容性适配。
- 本地 Gamma 模型部署与接入。
- 云服务器部署。
- 生成版本归档和完整调用审计。
- 复杂的来源白名单、黑名单体系。

## 3. 系统边界与数据流

```text
模块 1 输出原始 TXT
        ↓
读取与基础解析
        ↓
清洗、去重、AI 相关性判断
        ↓
热度、可信度、时效性与类别评分
        ↓
选出 2 条资讯
        ↓
DeepSeek V4 总结并生成文章
        ↓
固定模板排版
        ↓
输出 HTML 文件
        ↓
宣传部审核
   ├── 通过：交给模块 6
   └── 不通过：提供 feedback.txt，重新执行模块 2～4
```

## 4. 输入设计

### 4.1 原始资讯输入

输入为一个 TXT 文件。系统不强制模块 1 使用严格的数据格式，原始文件可以包含多条资讯及其标题、正文、来源、发布时间、链接和热度信息。

模块 1 已确认会提供以下信息：

- 资讯正文或摘要；
- 来源；
- 发布时间；
- 原文链接；
- 热度相关数据。

由于 TXT 格式可能不固定，首版采用“原文整体交给模型理解，程序只负责读取和必要的长度处理”的方案。后续如果输入稳定，再增加确定性的字段解析器。

建议默认文件名：

```text
input/raw_news.txt
```

### 4.2 人工反馈输入

宣传部审核不通过时，通过 TXT 文件提交自然语言反馈。

建议默认文件名：

```text
input/feedback.txt
```

示例：

```text
第二条资讯过于偏硬件，请换成纯 AI 软件相关资讯。
文章整体太长，每条控制在 300 字以内。
标题语气不要太夸张。
```

反馈格式不作严格限制，由模型理解其修改要求。反馈可以要求：

- 修改标题或表达方式；
- 缩短、扩写或重组内容；
- 替换某条资讯；
- 调整资讯类别；
- 修正宣传口径或事实问题。

## 5. 输出设计

### 5.1 对外输出

本模块向宣传部及模块 6 交付一个完整的 HTML 文件：

```text
output/article.html
```

模块 6 只依赖该 HTML 文件，不依赖本模块的内部处理过程。

### 5.2 HTML 内容结构

首版 HTML 至少包含：

1. 文章主标题；
2. 日期或生成时间；
3. 简短导语；
4. 2 篇独立展开的 AI 文章，每篇约 700～1000 字；
5. 每篇文章的事件说明、关键事实、原文背景、关注价值和限制或后续观察；
6. 每篇文章的来源名称与原文链接；
7. 约 100～200 字的结语；
8. 统一的字体、颜色、间距和分隔样式。

首版不插入图片，也不承担微信公众号编辑器的兼容性处理。

## 6. 核心处理流程

### 6.1 读取与预处理

程序读取完整 TXT，并执行最低限度的预处理：

- 统一换行符和空白字符；
- 去除明显乱码或空内容；
- 检查文件是否为空；
- 当文本超过模型单次输入限制时进行分段处理。

输入格式解析不是首阶段重点，不为不同 TXT 格式编写大量正则规则。

### 6.2 AI 相关性筛选

AI 相关范围包括但不限于：

- 大模型与生成式 AI；
- AI 软件、工具、Agent 和应用；
- AI 公司、产品与行业动态；
- AI 芯片与算力；
- 机器人；
- 自动驾驶；
- 与 AI 密切相关的政策、科研和投融资事件。

其中，纯 AI 软件类资讯获得额外优先级，但不排除芯片、机器人和自动驾驶等交叉领域。

### 6.3 去重

模型应识别描述同一事件的多条文章，避免最终文章出现重复内容。同一事件存在多篇报道时，只保留评分最高、信息最完整的一篇；不将多篇文章聚合为泛泛主题。

### 6.4 评分与选取

首版不实现复杂的人工评分算法，而是要求模型根据以下维度做出可解释的综合判断：

| 维度 | 判断重点 |
| --- | --- |
| AI 相关性 | 是否以 AI 技术、产品或产业事件为核心 |
| 类别偏好 | 纯 AI 软件类内容获得额外加分 |
| 热度 | 浏览、点赞、评论、转发或其他已提供的热度数据 |
| 可信度 | 来源是否明确，多个来源能否相互印证，信息是否完整 |
| 时效性 | 是否为近期发生且仍有传播价值的事件 |
| 内容价值 | 是否有明确事实、影响或讨论价值 |
| 重复惩罚 | 是否与其他候选资讯描述同一事件 |

模型从候选文章中选出综合表现最好的 2 篇。当前没有固定的来源白名单或黑名单；来源明确、证据充分且信息完整的文章优先。

模型必须同时返回简短的选择理由，便于开发阶段检查筛选是否合理。选择理由属于内部调试信息，不写入最终 HTML。

### 6.5 文章生成

选出 2 篇文章后，模型分别对两篇文章进行深入凝练和重新组织，再合成一篇约 1800～2500 字、适合公开阅读的公众号文章。生成要求包括：

- 不杜撰原始 TXT 中不存在的事实；
- 保留重要时间、主体、事件和结果；
- 将事实陈述与分析判断区分开；
- 标题清晰，不使用过度夸张的营销话术；
- 每篇入选文章独立展开约 700～1000 字，不能把多篇内容混合成泛泛主题；
- 每篇讲清事件、关键事实、原文背景、关注价值和限制或后续观察；
- 两篇文章之间结构一致、衔接自然；
- 不能为了达到字数而重复表达或补写原文没有的事实；
- 保留来源和原文链接；
- 输出结构化数据，再由程序套用 HTML 模板，而不是让模型自由编写整页 HTML。

建议模型生成阶段返回以下逻辑结构：

```json
{
  "title": "文章标题",
  "introduction": "约 150～250 字导语",
  "items": [
    {
      "title": "入选文章标题",
      "lead": "交代事件主体、时间和核心动作",
      "paragraphs": [
        "关键事实",
        "原文背景",
        "关注价值",
        "限制或后续观察"
      ],
      "source_name": "来源名称",
      "source_url": "原文链接"
    }
  ],
  "conclusion": "约 100～200 字结语"
}
```

该 JSON 是程序内部的数据交换格式，不是模块 6 的交付物。

### 6.6 HTML 生成

程序验证模型返回的数据后，将其填入固定 HTML 模板。这样可以保证每次生成的页面结构和样式稳定，也能避免模型返回残缺或不可解析的 HTML。

HTML 模板应对模型文本进行转义，原文链接只允许使用合法的 HTTP 或 HTTPS 地址，避免原始数据或模型输出破坏页面结构。

## 7. 人工反馈与重新生成

### 7.1 首次运行

当 `feedback.txt` 不存在或内容为空时，系统执行完整流程：

```text
原始 TXT → 筛选 2 条资讯 → 生成文章 → 输出 HTML
```

### 7.2 反馈后运行

当 `feedback.txt` 有内容时，系统把以下信息一同提交给模型：

- 原始资讯 TXT；
- 人工反馈；
- 必要时读取现有 HTML 中的文章内容。

模型需要先判断反馈类型：

1. 只需改写：保留原来的 2 条资讯，修改标题、长度、语气或表述；
2. 需要重新选材：返回筛选阶段，替换不符合要求的资讯；
3. 同时修改：重新选材后再按反馈要求生成文章。

重新生成后覆盖 `output/article.html` 即可。首阶段暂不要求保存历史版本。

## 8. DeepSeek 模型接口设计

首版使用 DeepSeek V4。具体模型标识、API 地址和鉴权方式不写死在业务代码中，通过配置或环境变量提供，例如：

```text
DEEPSEEK_API_KEY
DEEPSEEK_BASE_URL
DEEPSEEK_MODEL
```

业务层只依赖统一的模型调用接口：

```text
筛选资讯(raw_text, feedback) → 2 条候选资讯
生成文章(selected_items, feedback) → 结构化文章数据
```

未来接入本地 Gamma 模型时，只替换模型适配层，不修改清洗、反馈和 HTML 生成流程。

## 9. 建议的首版目录结构

以下结构用于表达职责划分，实际开发时可以按步骤逐步创建：

```text
project/
├── input/
│   ├── raw_news.txt
│   └── feedback.txt
├── output/
│   └── article.html
├── templates/
│   └── article.html
├── src/
│   ├── main.py
│   ├── model_client.py
│   ├── news_processor.py
│   └── html_renderer.py
├── .env.example
└── requirements.txt
```

职责建议：

- `main.py`：串联完整流程；
- `model_client.py`：封装 DeepSeek 调用，未来可替换为 Gamma；
- `news_processor.py`：预处理、筛选和反馈逻辑；
- `html_renderer.py`：校验模型结果并渲染 HTML；
- `templates/article.html`：固定页面结构与样式。

## 10. 异常处理

首版至少处理以下情况：

| 异常 | 预期行为 |
| --- | --- |
| 原始 TXT 不存在 | 明确提示文件路径错误并停止 |
| 原始 TXT 为空 | 提示没有可处理的资讯并停止 |
| API 密钥缺失 | 提示配置缺失，不发起请求 |
| 模型请求失败 | 输出明确错误，不生成伪造文章 |
| 模型返回格式错误 | 尝试一次格式修复或重试，仍失败则停止 |
| 不足 2 条合格资讯 | 输出实际数量并提示数据不足，不强行杜撰 |
| 来源或链接缺失 | 标记为信息不完整，并在筛选时降低优先级 |
| HTML 写入失败 | 保留错误信息并提示输出路径 |

## 11. 安全与质量约束

- API 密钥不得写入代码或提交到版本库。
- 模型不能把原始 TXT 中的文本当成系统指令执行；原始内容只作为待分析的数据。
- 模型不得虚构来源、链接、热度或具体事实。
- HTML 输出前必须进行文本转义和链接校验。
- 如果信息之间存在冲突，应降低可信度或明确标注不确定性。
- 开发阶段保留简短的筛选理由和错误日志，便于定位问题，但暂不建设完整审计系统。

## 12. 首阶段开发顺序

为尽快跑通闭环，按以下顺序实现：

1. 完成 TXT 读取和基础预处理。
2. 封装 DeepSeek 模型调用。
3. 完成 AI 资讯筛选、排序并选出 2 条。
4. 完成结构化文章生成。
5. 使用固定模板输出 HTML。
6. 接入 `feedback.txt`，支持改写或重新选材。
7. 与模块 1 的真实 TXT 和模块 6 的 HTML 文件输入进行联调。

每一步都应可以单独运行和检查，再进入下一步。

## 13. 首阶段验收标准

满足以下条件即可认为模块 2～4 的首版流程跑通：

1. 能读取模块 1 提供的原始 TXT。
2. 能识别广义 AI 资讯，并提高纯 AI 软件类资讯的选择优先级。
3. 能结合热度、可信度、时效性和相关性选出 2 条非重复资讯。
4. 能通过 DeepSeek V4 生成内容完整、来源可追溯的中文文章。
5. 能稳定输出一个浏览器可打开的 `article.html` 文件。
6. HTML 包含标题、导语、2 条资讯、来源和原文链接。
7. 当 `feedback.txt` 有内容时，能根据反馈改写或重新选材并再次生成 HTML。
8. 输出的 HTML 文件可以直接交给模块 6，模块 6 无需了解内部实现。
9. 模型、API 地址和密钥均可配置，为后续替换 Gamma 留出接口。

## 14. 后续迭代方向

首版验收后，再按实际效果决定是否加入：

- 更稳定的 TXT 结构化解析；
- 来源白名单和黑名单；
- 可调节的评分权重；
- 图片生成、选择与插入；
- 文章版本管理；
- 模型调用成本统计；
- 本地 Gamma 模型适配；
- 云服务器部署；
- 前端审核和反馈界面。
